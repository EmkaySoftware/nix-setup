# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal NixOS flake configuration (flake-based, `nixos-unstable` + `home-manager`). Single machine (`northwind`) and single user (`absta`) are currently defined. There is no CI, build script, or test suite — validation happens by building/switching the NixOS configuration on the target machine.

## Commands

There is no sandboxed way to build this from an arbitrary dev machine (it targets specific hardware via `machines/northwind/hardware.nix`). On the actual machine:

```sh
# Rebuild and switch to the new generation
sudo nixos-rebuild switch --flake .#northwind

# Check the flake evaluates / build without switching
nixos-rebuild build --flake .#northwind
nix flake check

# Format nix files (if nixpkgs-fmt/alejandra/nixfmt is available)
nix fmt
```

When editing `.nix` files without machine access, the best available verification is `nix flake check` or `nix eval` — there's no test harness.

## Architecture

The repo models configuration as a hierarchy. The `README.md` diagram (`Machine -> User -> Profile -> Feature`) describes an earlier design; profiles have since been removed in favor of a flatter, list-driven scheme:

```
Machine (1) -> User (1..*) -> active-modules.nix (list of names) -> modules/<name>/{nixos,home}
```

- **Machine** (`machines/<name>/`): hardware-specific and physical-machine config — boot, networking, audio, hardware. `machines/northwind/hardware.nix` is generated by `nixos-generate-config` and should not be hand-edited.
- **User** (`users/<name>/`): config for one person (potentially spanning more than one account for that person — not necessarily 1:1 with a single Unix user). Holds account definition (`user.nix`), nix settings (`nix.nix`), locale/timezone (`region.nix`), the active-module list (`active-modules.nix`), and the user's `home/` directory (home-manager config, wired in separately by `flake.nix`).
- **Module** (`modules/<name>/{nixos,home}/default.nix`): the concrete installation of one piece of software, split by which module tree it belongs to — `nixos/default.nix` for system-level config, `home/default.nix` for home-manager-level config. Not every module needs both sides (e.g. `modules/greetd/` is nixos-only). Modules stay generic/enablement-only (e.g. `programs.git.enable = true;`) — no personal data.

### `active-modules.nix` + `modules/lib.nix` — the single source of truth for what's installed

`users/<user>/active-modules.nix` is a plain list of module names, e.g.:

```nix
[ "hyprland" "greetd" "git" ]
```

`modules/lib.nix` exports `mkModules type names`, which resolves each name in the list to `modules/<name>/<type>/default.nix` — for `type` `"nixos"` or `"home"` — and silently skips a name that has no variant of that type. Both `users/<user>/default.nix` (NixOS side) and `users/<user>/home/default.nix` (home-manager side) import the *same* `active-modules.nix` list and call `mkModules` with their own type:

```nix
# users/absta/default.nix (nixos)
{ lib, ... }:
let
  modLib = import ../../modules/lib.nix { inherit lib; };
  active = import ./active-modules.nix;
in {
  imports = [ ./user.nix ./nix.nix ./region.nix ] ++ modLib.mkModules "nixos" active;
}
```

```nix
# users/absta/home/default.nix (home-manager)
{ lib, ... }:
let
  modLib = import ../../../modules/lib.nix { inherit lib; };
  active = import ../active-modules.nix;
  userConfig = lib.filter builtins.pathExists (map (n: ./. + "/${n}.nix") active);
in {
  imports = modLib.mkModules "home" active ++ userConfig;
}
```

This is the only place "is this module active" is decided — there is no `profiles.<name>.active` option anymore, and no `lib.mkIf` gating inside module or user files. Activation is just list membership, checked with `builtins.pathExists`/`mkModules` before the module system ever runs, so there's nothing that needs to be unconditionally declared elsewhere (the old design's failure mode: referencing `config.profiles.<name>.active` when nothing declared it).

### `users/<name>/home/<name>.nix` owns identity, `modules/` owns software

Personal values for an active module — git username/email, hyprland monitors/keybinds, etc. — live in a same-named file directly under `users/<name>/home/`, e.g. `users/absta/home/git.nix`, `users/absta/home/hyprland.nix`. These files are **plain, unconditional module bodies** (no `mkIf`, no `config` check) — the `userConfig` line above (`lib.filter builtins.pathExists ...`) only imports a personal file when its name is also in `active-modules.nix`, so activation is enforced once, at the import-list level, not duplicated inside every file. Not every active module needs a personal file (e.g. there's no `greetd.nix` under `users/absta/home/` — nothing user-specific to say about the greeter).

### Known gaps

- **`profiles/` and `features/` are dead code.** Nothing reachable from `flake.nix` imports them anymore (the last references were removed when `users/absta/{,home/}modules.nix` were replaced by the `active-modules.nix` scheme). `profiles/development.nix` (which pulled in `features/development/ide/codium.nix`) was never migrated to a `modules/` entry, so codium/VSCode is currently not installed by any active configuration. Both directories are candidates for deletion once anything still worth keeping (e.g. codium) is ported to `modules/`.
